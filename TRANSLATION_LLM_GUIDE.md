# LLM через GitHub Models: как получить чистый черновик

## Почему LLM чище, чем OPUS/NLLB

- OPUS-MT (300 МБ, 2019) и даже NLLB — это чистые MT-модели: они обучены на параллельных корпусах
  и часто просто транслитерируют архаизмы: `gaol→гаол`, `gaoler→гаолер`, `garnish→гарнир`, `tap→кран`.
  Это и даёт «большой пласт в запрещённых» — глоссарий на 22 варианта вынужден править каждую страницу.
- LLM (7-70B) видела гораздо больше русской исторической прозы и при правильном промпте
  сама даёт `тюрьма/тюремщик/вступительный побор/тюремный кабак`, лучше держит длинный период
  (медиана 19 слов, макс. 315) и не рвёт предложения на границах сегментов.

Trade-off: LLM на CPU — 3-4с/предложение (десятки часов на книгу) и риск отсебятины/потерь чисел.
Поэтому в этой книге:

* качество важнее скорости → разбиваем на части,
* числа/сноски проверяем `mt_report.py` до ручной правки,
* глоссарий остаётся `post_replace` (скрипт `apply_glossary.py`).

## Что уже сделано

- `tools/translate_github_models.py` — перевод через `https://models.github.ai/inference/chat/completions`
  с `GITHUB_TOKEN` (разрешение `models: read`). Берёт `work-doc.json`, для каждого абзаца
  собирает релевантный кусок глоссария и переводит с `temperature=0.2`.
- `tools/translate_nllb.py` — контрольный NLLB (600M) для сравнения с OPUS.
- `tools/apply_glossary.py` — детерминированная замена `rejected → ru`.
- `.github/workflows/translate-compare.yml` — параллельный прогон трёх движков на одних разворотах.

## Как запустить сравнение (2 минуты)

1. GitHub → Actions → `Compare translation models (OPUS vs NLLB vs LLM)` → Run workflow
2. Ветка `arena/b1f6ea5c-govard-book`
3. `limit`: `31,87,141,95` (набор из `TRANSLATION_PLAN` — иностранные тюрьмы, Ньюгейт, заключение, Англия)
4. `llm_model`: `openai/gpt-4o-mini` (дефолт, дёшево и стабильно) или `meta/Meta-Llama-3.1-405B-Instruct`,
   `mistral-ai/mistral-small-2503` и т.д.
5. `apply_glossary`: `true` (рекомендуется)

Через ~10 минут в issue №2 придут 3 комментария с логами/отчётами и 3 артефакта:
`mt-draft-opus`, `mt-draft-nllb`, `mt-draft-llm`. В отчёте сравниваем:
`чисел потеряно/добавлено`, `расхождение сносок`, `запрещённые варианты`.

## Интерпретация

- Если у LLM `запрещённых` 0, а у OPUS/NLLB 2 — значит промпт+модель уже закрывает часть глоссария.
- Но это не значит, что глоссарий не нужен: LLM может внезапно дать «бридвелл» на 120-м развороте,
  а `post_replace` это поймает. Поэтому оставляем оба слоя: промпт + скрипт.

## После выбора

Полный прогон — тем же workflow, только `limit` пустой или по частям:
`limit=1,2,3,4,5,6,...` (до 15 за раз), лимит задачи 300 мин. Дальше — как и раньше:
`mt_report → ручное редактирование → ru_translations_v2.py`.

## GPU-опция

` tencent/Hunyuan-MT-7B` — лучший открытый MT на 2026, 16 ГБ, требует GPU-раннер
(`runs-on: gpu` + оплата). Даёт ещё более точные числа, чем NLLB, без отсебятины LLM.
Держим как «если NLLB/LLM не хватит».

## Важно

- Никаких ключей в чат присылать не нужно: `GITHUB_TOKEN` генерируется Actions автоматически,
  доступ к Models выдаётся по нажатию `Enable` в Settings → Models (если спросит).
- Если Models недоступен в регионе/орг — workflow с LLM упадёт, два других всё равно отработают.
  Тогда можно прогнать LLM локально и прислать `ru-mt.json` (вариант C из `TRANSLATION_HF_ACCESS.md`).
